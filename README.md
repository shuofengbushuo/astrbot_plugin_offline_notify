## 功能概览

| 功能 | 说明 |
|------|------|
| LLM 内容生成 | 调用对话模型生成多样化、自然的下线通知，每次内容风格不同 |
| 被动窗口事件驱动 | **插件层**划定下线时间前后的时间窗口，窗口内目标群有人发言即借被动 msg_id 发送（每日流程设计如此）。⚠️ 但 QQ 官方**客户端适配器并不校验 5 分钟时效**：它在进程内永久缓存 `_session_last_message_id` / `_session_scene`，且每次自己发完都把已发 id 写回缓存——因此群只要历史上活跃过，即使长期空闲，适配器仍可借缓存 msg_id 被动回复，或在 `scene=="group"` 缓存下**主动推送**（无需 msg_id）。故 WebUI「测试发送」/ 手动发送常常离窗口也能成功；每日流程则是插件刻意做成事件驱动，并非适配器做不到离窗口发送 |
| 模板回退 | LLM 生成失败时自动回退到内置消息模板，确保通知不丢失 |
| 定时监听窗口 | 基于 APScheduler 拆成「监听开始 / 监听结束」两个 cron：监听开始进入 armed 状态监听目标群消息，监听结束仅清理窗口状态（窗口内没机会则本次不发送，无兜底补发） |
| 差异化时间 | 工作日、周末、特定日期可设置不同的下线时间 |
| 多群组通知 | 同时向多个QQ群发送下线提醒 |
| 自定义模板 | 标题、正文、表情符号、底部文字均可自定义 |
| 通知预览 | WebUI 和命令均可预览通知消息效果 |
| 失败重试 | 消息发送失败自动重试，间隔递增 |
| 自我监控 | 心跳检测调度器状态，异常时自动告警 |
| 告警双通道 | 支持向QQ群或QQ私聊发送告警信息 |
| 发布记录 | 持久化存储通知发送历史，支持 WebUI 和命令查询 |
| 手动生成 | 管理员可在私聊中生成通知并发送到指定群，与自动调度共用同一条自定义提示词 |
| LLM 通用提示词 | 离线通知以**通用、中立的默认提示词**生成离场说明（规避 AI/系统口吻与「XX:XX 下线」字眼，借 `{time_context}` 自然说明离开理由），长内容合并为单条发送（换行保留分句节奏） |
| 定时计划命令管理 | 通过 QQ 聊天命令 `/下线通知 计划` 可视化增删改、启用/禁用定时计划，**无需编辑 JSON 配置**；变更即时热重载，无需重启插件 |

> **v2.0.0 起仅支持 QQ 官方机器人（`qq_official` / `qq_official_webhook`）平台，不再支持 `aiocqhttp`（OneBot/NapCat/go-cqhttp）。**

## 快速开始

1. 在 AstrBot WebUI 的「插件管理」中启用本插件
2. 在 **LLM 通知内容生成** 配置中选择一个对话模型提供商
3. 在插件配置中填写**目标通知群组**的群 openid（32 位十六进制串）
4. 在配置中设置**窗口提前开启 / 延后关闭**与**触发时机浮动**（默认各 30 / 30 / 5 分钟）
5. 用聊天命令 `/下线通知 计划 添加 工作日下线 工作日 23:00` 添加定时计划（无需编辑 JSON）
6. 使用 `/下线通知 生成` 命令查看 LLM 实时生成效果
7. 使用 `/下线通知 计划 列表` 命令查看所有计划

## 配置说明

### 基础配置

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| 窗口提前开启 | 整数 | 30 | 在下线时间前 N 分钟进入时间窗口，开始监听目标群消息，范围 0-180 分钟 |
| 窗口延后关闭 | 整数 | 30 | 在下线时间后 N 分钟结束监听窗口（仅清理状态，不发送）；窗口内始终无人发言则本次不发送，范围 0-180 分钟 |
| 触发时机浮动 | 整数 | 5 | 检测到目标群消息后随机延迟 0~N 分钟再发送，模拟自然节奏；上限受 QQ 官方被动 msg_id 5 分钟有效期约束，范围 0-5 分钟 |

#### 被动窗口机制说明

> **v2.0.0 重构**：放弃「到点主动推送」，改为「时间窗口 + 事件驱动」。

QQ 官方群消息分两种：**被动回复**（需挂载较新的 `msg_id`，不占主动配额）与**主动推送**（占官方主动消息配额）。原「到点主动推」在深夜群里没人说话时，往往没有新鲜 msg_id，只能走主动推送甚至被服务端拒收。（注：客户端适配器其实在 `scene=="group"` 缓存下可主动推送，并不「静默丢弃」——详见下文「会话缓存」；v2.0.0 改为事件驱动是插件层的设计取舍。）

新机制划定一个时间窗口 `[下线时刻 − 窗口提前开启, 下线时刻 + 窗口延后关闭]`，窗口内一旦检测到目标群有人发言（产生了新鲜 msg_id），立即「借」这条被动消息的窗口把下线通知发出去。

**工作原理**：

```
下线时间 23:00，窗口提前开启 30 分钟，窗口延后关闭 30 分钟

22:30 ── 监听开始：进入监听状态（armed）
  │
  ├─ 22:30 ~ 23:30 内目标群有人发言 ── 命中 msg_id，随机延迟 0~5 分钟后发送
  │
  └─ 23:30 监听结束：窗口内始终无人发言 → 本次不发送（插件 `_precheck` 拦掉无 msg_id 的主动推送；适配器在 scene=="group" 缓存下本可主动推送，但本插件默认不放开，故无兜底）
```

**触发条件**（同时满足才发送）：计划处于窗口内 ∧ 今日未发送（去重）∧ 收到一条目标群消息。

### 定时通知计划

> **v1.6.0 重大简化**：定时计划 **不再需要编辑 JSON 配置**，改用 QQ 聊天命令（`/下线通知 计划`）或 WebUI 管理面板可视化增删改，变更即时热重载，无需重启插件。**窗口与触发时机改为全局统一控制**——计划只关心「何时下线」，窗口提前/延后与触发浮动由配置面板统一决定。

计划数据持久化在插件数据目录的 `schedules.json`，完全由 `/下线通知 计划` 命令或 WebUI 管理面板维护，不再依赖 JSON 配置。

#### 默认计划

插件首次加载时若没有任何计划，会自动创建以下两个：

| 计划名称 | 日期类型 | 下线时间 | 状态 |
|----------|----------|----------|------|
| 工作日下线 | 工作日（周一至周五） | 23:00 | 启用 |
| 周末下线 | 周末（周六、周日） | 23:20 | 启用 |

> 窗口提前开启、窗口延后关闭、触发时机浮动均为**全局设置**，对所有计划统一生效（见 [基础配置](#基础配置)）。

#### 计划字段说明

| 字段 | 类型 | 允许值 | 说明 |
|------|------|--------|------|
| `name` | 文本 | 任意字符串 | 计划名称，用于日志和状态显示，便于区分不同计划 |
| `day_type` | 枚举 | `everyday`（每天）、`weekday`（工作日）、`weekend`（周末）、`specific`（特定日期） | 决定该计划在哪些日期生效 |
| `specific_days` | 列表 | `monday`、`tuesday`、`wednesday`、`thursday`、`friday`、`saturday`、`sunday` | 仅当 `day_type` 为 `specific` 时生效，选择具体的星期几 |
| `offline_time` | 文本 | 24小时制 `HH:MM` 格式，如 `22:30`、`23:00`、`00:00` | 设定的 AI 下线时间 |
| `enabled` | 开关 | 开启 / 关闭 | 启用或禁用该计划。禁用后该计划不会创建定时任务 |

> **v2.0.0**：计划级 `float_range` 已移除（触发时机浮动改为全局配置）。`schedules` 配置项已从配置面板移除，计划完全由命令/面板管理。

#### 通过命令管理计划（推荐）

详见 [命令列表](#命令列表) 中的 `/下线通知 计划` 命令组，常用示例：

```
/下线通知 计划 列表
/下线通知 计划 添加 工作日下线 工作日 23:00
/下线通知 计划 添加 周末晚安 周末 23:30
/下线通知 计划 修改 工作日下线 时间 22:30
/下线通知 计划 禁用 周末下线
/下线通知 计划 删除 旧计划
```

> 时间参数中英文冒号均可、空格自动忽略：`10: 30` / `10：30` 都会被正确解析为 `10:30`。

### LLM 通知内容生成

> **v1.1.0 新增功能**：调用对话模型自动生成多样化、自然的下线通知内容。

启用后，系统将使用对话模型实时生成通知消息，而非使用固定的模板文本。每次生成的通知内容风格都有变化，更加自然和人性化。

#### 配置项

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| 启用 LLM 生成通知 | 开关 | 开启 | 开启后使用对话模型生成通知内容，关闭则使用消息模板 |
| LLM 提供商 | 下拉选择 | 空 | 选择用于生成通知内容的对话模型。**必须选择一个有效的提供商才能使用 LLM 生成** |
| LLM 调用超时 | 整数（秒） | 15 | LLM 生成通知的最大等待时间，范围 5-60 秒 |
| 失败时回退到模板 | 开关 | 开启 | LLM 生成失败（超时/异常）时，自动使用消息模板作为备用 |
| 自定义提示词 | 文本 | （内置通用默认） | **明置编辑**。自动调度与手动触发的通知共用同一条提示词。留空用内置通用默认（即本项默认值），填写后整体覆盖。支持占位符 `{date}` `{day_of_week}` `{time_context}` `{offline_time}` `{countdown_minutes}` |

#### 内置默认提示词

系统使用以下内置默认提示词（`DEFAULT_PROMPT`，即 `custom_prompt` 默认值）引导 LLM 生成通知。该提示词为**通用、中立的功能引导**，不含任何特定人设 / 语气风格，仅规范基本指令与输出形式；自动通知与手动触发共用同一条，并支持在配置面板用 `custom_prompt` 覆盖（见下方「自定义提示词」）：

```
你是一个用于生成「暂时离开群聊通知」的文本生成助手。当触发方需要暂时离开当前群聊时，你会生成一段简洁的离场说明，由触发方发送到对应群聊。

系统会在调用时注入以下上下文（请勿在消息中复述变量名或占位符）：
- {time_context}：当前离场的情境说明（例如：准备去休息 / 临时有事 / 想稍作停顿），据此自然说明离开原因。
- {date} {day_of_week}：当前日期与星期。

生成要求：
1. 内容聚焦「暂时离开」这一事实，用一两句话说明接下来要去做的事（参照 time_context 的情境），避免使用「下线 / 离线 / 退出 / 挂机 / 系统 / 通知 / 机器人 / AI / 助手」等词汇或后台公告式口吻。
2. 保持中立、平实的表述，不设定任何特定人设、性格、年龄或语气风格。
3. 纯文本输出，不使用 Markdown、不添加前缀或解释、不包含 <think> 标签。
4. 仅输出最终要发送的那一两句话，不要输出其他内容。

当前日期: {date} {day_of_week}
```

> `{time_context}` 由插件按当前小时自动注入（深夜去睡觉 / 傍晚休息 / 下午有事 / 上午有事），据此自然说明离开理由——既不暴露 AI 身份、也不写具体下线时刻。输出为 1-2 句离场说明，较长时由本插件按句自动分段发送（与 splitter 风格一致且无需依赖 splitter 启用）。如需保留原先的「砂糖」风格，可在配置项 `custom_prompt` 中粘贴该提示词。

#### 自定义提示词

在配置面板填写 `自定义提示词`（即 `custom_prompt`）即可覆盖内置默认，留空则用内置通用默认。自动与手动通知共用同一条。

> **v2.0.0 说明**：`/下线通知 提示词` 命名方案库命令（保存 / 切换 / 删除多套方案）已移除。底层 `PromptStore` 能力仍保留——**此前已保存并激活的方案仍然生效**（优先级仍高于 `custom_prompt`）；如需停用，编辑插件数据目录的 `prompts.json` 将 `active` 置空即可。新建/切换方案请直接改 `custom_prompt`。

#### LLM 生成 vs 模板引擎

| 特性 | LLM 生成 | 模板引擎 |
|------|----------|----------|
| 内容多样性 | 每次不同，风格多变 | 始终相同，仅变量替换 |
| 自然度 | 像真人写的通知 | 固定格式 |
| 响应速度 | 取决于 LLM 响应时间（通常 1-5 秒） | 即时 |
| 依赖 | 需要配置 LLM 提供商 | 无需外部依赖 |
| 可靠性 | 可能超时或失败，但会自动回退 | 始终可用 |

#### 工作流程

```
定时触发
  │
  ▼
尝试 LLM 生成 ◄── 启用 LLM 生成？ ──► 否 ──► 使用模板引擎
  │                                           │
  ├─ 成功 ──► 使用 LLM 生成的内容            │
  │                                           │
  └─ 失败 ──► 回退到模板？ ──► 是 ──► 使用模板引擎
                  │
                  └─ 否 ──► 跳过本次通知
```

### 消息模板（回退方案）

消息模板控制通知消息的外观和内容。支持使用 `{变量名}` 插入动态内容。

#### 标题模板

**说明**：通知消息的标题行，通常用方括号包裹以突出显示。

**可用变量**：

| 变量 | 说明 | 示例值 |
|------|------|--------|
| `{time}` | 下线时间 | `23:00` |
| `{date}` | 当前日期 | `2026-07-07` |
| `{day_of_week}` | 星期几（中文） | `周二` |
| `{countdown_minutes}` | 剩余分钟数 | `5` |

**默认值**：`【AI服务下线通知】`

**使用示例**：

| 模板内容 | 渲染结果 |
|----------|----------|
| `【AI服务下线通知】` | `【AI服务下线通知】` |
| `【{day_of_week}下线提醒】` | `【周二下线提醒】` |
| `【{date} AI下线】` | `【2026-07-07 AI下线】` |

---

#### 正文模板

**说明**：通知消息的主体内容，是群成员看到的核心信息。

**可用变量**：

| 变量 | 说明 | 示例值 |
|------|------|--------|
| `{time}` | 下线时间 | `23:00` |
| `{date}` | 当前日期 | `2026-07-07` |
| `{day_of_week}` | 星期几（中文） | `周二` |
| `{countdown_minutes}` | 剩余分钟数 | `5` |
| `{emoji}` | 用户配置的表情符号 | `🌙` |

**默认值**：

```
各位成员请注意~

{emoji} AI助手即将在 {time} 下线休息，预计还有 {countdown_minutes} 分钟。

如有需要请尽快处理未完成的事项。
明天见！晚安~
```

**渲染示例**（假设当前为周二 22:55，下线时间 23:00）：

```
各位成员请注意~

🌙 AI助手即将在 23:00 下线休息，预计还有 5 分钟。

如有需要请尽快处理未完成的事项。
明天见！晚安~
```

**自定义示例**：

| 模板内容 | 渲染结果 |
|----------|----------|
| `晚安！AI将在 {time} 休息~` | `晚安！AI将在 23:00 休息~` |
| `{emoji} 还有 {countdown_minutes} 分钟就下线啦！` | ` 还有 5 分钟就下线啦！` |
| `今天是 {day_of_week}，{time} 准时下线哦~` | `今天是 周二，23:00 准时下线哦~` |

#### 表情符号

**默认值**：`🌙`

**常用推荐**：

| 符号 | 含义 |
|------|------|
| `🌙` | 月亮（晚安） |
| `😴` | 睡觉 |
| `💤` | 休息 |
| `🌟` | 星星 |
| `👋` | 再见 |

### 目标群组

配置需要接收下线通知的QQ群列表。

| 字段 | 类型 | 说明 |
|------|------|------|
| `group_id` | 文本 | QQ群号，必填。请确保机器人已加入该群 |
| `group_name` | 文本 | 群名称备注，仅用于管理界面显示，不影响功能 |
| `enabled` | 开关 | 启用或禁用该群组的通知。禁用后该群不会收到通知 |

**注意**：如果未配置任何群组，通知将不会发送到任何地方。

### 重试配置

消息发送失败时的自动重试策略。

| 配置项 | 作用对象 | 类型 | 默认值 | 允许范围 | 说明 |
|--------|----------|------|--------|----------|------|
| 消息发送重试次数 (`send_retries`) | 把通知**消息发给群** | 整数 | 3 | 0-10 | 发送失败（平台实例找不到、被动窗口未就绪等）时重试，每次间隔递增。0 = 不重试 |
| 发送重试基础间隔 (`send_retry_interval`) | 同上 | 整数（秒） | 10 | 5-120 | 实际等待 = 基础间隔 × 当前重试次数 |
| LLM 生成重试次数 (`llm_retries`) | **调用 LLM 生成内容** | 整数 | 2 | 0-5 | 生成超时 / 失败后，等待 `llm_retry_interval` 秒再试。0 = 只试一次不重试 |
| LLM 重试前等待 (`llm_retry_interval`) | 同上 | 整数（秒） | 3 | 1-30 | 给 provider 注册表恢复时间 |

> 历史上曾同时存在「最大重试次数」与「LLM 调用重试次数」两个易混淆的项；现已重塑为上述两组**正交**配置：一组管「发消息」、一组管「生成内容」，互不干扰。发送重试不消耗 LLM 配额，LLM 重试只在生成阶段发生。

### 自我监控配置

定时任务的健康检查和异常告警功能。

| 配置项 | 类型 | 默认值 | 允许范围 | 说明 |
|--------|------|--------|----------|------|
| 启用自我监控 | 开关 | 开启 | - | 关闭后不再进行心跳检测和告警 |
| 心跳检测间隔 | 整数（秒） | 300 | 60-3600 | 每隔 N 秒检查一次调度器是否正常运行 |
| 心跳超时阈值 | 整数（秒） | 180 | - | 调度器心跳年龄超过此值视为异常，默认为心跳检测间隔的 3 倍 |
| 告警通知群号 | 文本 | 空 | - | 调度器异常时，向此 QQ 群发送告警消息。留空则仅记录日志 |
| 告警通知QQ号 | 文本 | 空 | - | 调度器异常时，向此 QQ 号发送私聊告警消息。留空则不发送私聊告警 |

**告警触发条件**：

1. 调度器未运行（插件启动失败或被意外停止）
2. 调度器心跳超时（超过 3 倍心跳间隔未更新）

**告警冷却机制**：同一异常不会重复告警，两次告警之间至少间隔 30 分钟，避免告警轰炸。

**双通道告警**：`告警通知群号` 和 `告警通知QQ号` 可同时填写，异常时会同时向群和私聊发送告警。也可以只填其中一个，实现单通道告警。

### 手动生成命令（管理员专用）

> **v1.3.0 新增**：支持管理员在私聊中生成通知并发送到指定群。

#### 使用方式

在**私聊**中向机器人发送：

```
/下线通知 生成 [群 openid]
```

例如：`/下线通知 生成 7CA0B1BF3E5D4A8C9F2B6E1D0A4C8B93`

> QQ 官方下必须填群 openid（32 位十六进制串），不是数字群号。获取方式：让机器人在目标群里收一条消息，日志中的 `session_id` 即 openid。

#### 权限控制

- **群聊模式**：`/下线通知 生成` 仅预览 LLM 生成结果，不发送
- **私聊模式**：`/下线通知 生成 [群 openid]` 仅管理员可用，非管理员会收到权限不足提示

#### 手动生成的提示词

手动生成（`/下线通知 生成 [群 openid]`）与自动调度**共用同一条提示词**（`custom_prompt` / `DEFAULT_PROMPT`），不再区分「自动/手动」两套。若希望手动场景语气略有不同，可在提示词中用 `{offline_time}` `{countdown_minutes}` 等占位符自然容纳可选的下线时间信息。

#### 工作流程

```
私聊：/下线通知 生成 [群 openid]
  │
  ├─ 权限校验 ──► 非管理员 ──► 拒绝
  │
  ├─ 格式校验 ──► 群号格式错误 ──► 提示
  │
  ├─ 调用 LLM 生成（共用 custom_prompt）
  │     │
  │     ├─ 成功 ──► 发送到指定群
  │     │
  │     └─ 失败 ──► 回退模板 ──► 发送到指定群
  │
  └─ 返回结果给管理员
```

### 调度器心跳机制

> **v1.3.0 新增**：调度器内部维护独立心跳，用于监控器判断调度器事件循环是否仍在运行。

#### 工作原理

- 调度器启动后，内部创建异步心跳任务，每 60 秒更新一次心跳时间戳
- 监控器通过检查心跳年龄判断调度器健康状态
- 心跳超时阈值：3 倍心跳检测间隔（默认 180 秒）
- 心跳超时触发告警（遵循告警冷却机制）

此机制确保即使 APScheduler 内部异常，监控器也能及时发现并告警。

## 协议适配（QQ 官方机器人）

> **v2.0.0 起仅支持 QQ 官方机器人 API（`qq_official` / `qq_official_webhook`），不再支持 `aiocqhttp`（OneBot/NapCat/go-cqhttp）。**

### QQ 官方协议的关键约束

| 维度 | 说明 |
|------|------|
| 群标识 | `group_openid`，32 位十六进制串 |
| 私聊标识 | `user_openid`（C2C） |
| 群被动回复 | 服务端规则：被动回复需挂载**较新**的 `msg_id`。⚠️ **客户端适配器不校验 5 分钟时效**——它永久缓存 `_session_last_message_id`（且每次发送后把已发 id 写回），只做 `dict.get()`，因此陈旧的缓存 msg_id 也会被当作「有效」继续使用 |
| 群主动推送（离窗口路径） | `_allow_group_proactive_send` 默认 `True`；只要该群 `_session_scene=="group"` 曾被缓存（群历史上收过消息），适配器即可**不带 msg_id** 直接主动推送，真正与「5 分钟窗口」无关，但占用官方主动消息配额 |
| 群主动推送 | 占用官方主动消息配额 |
| 私聊主动推送 | C2C 支持主动推送，**不受 msg_id 限制** |
| 默认消息格式 | Markdown（`msg_type=2`），需在开放平台报备模板；本插件强制纯文本 |
| 长通知 | **合并为单条**（换行保留分句节奏），节省配额、规避频控 |

### 插件的适配行为

| 行为 | 说明 |
|------|------|
| 长通知分段 | **合并为单条**发送，逐段发送会成倍消耗配额并易触发频控 |
| 消息格式 | **强制纯文本**，避免未报备 Markdown 模板报错 |
| 群标识校验 | 要求 openid（32 位十六进制串），数字群号会直接报错 |
| 发送前检查 | 探测适配器缓存的被动 `msg_id` / `scene` 是否存在（`inspect_qq_official_session` 只查**存在性**、不查时效）；缺失且未开 `allow_proactive` 时判失败并说明真实原因。⚠️ 若 `platform_ids` 配错使平台解析失败，此检查整体跳过，判定权交给适配器 |
| 被动窗口触发 | **每日流程**窗口内命中目标群消息才发送（借被动 msg_id，不占主动配额）。这是插件刻意设计；适配器本身离窗口也能发（见下方「会话缓存」） |

### QQ 官方适配器的会话缓存（离窗口发送的关键）

> **v2.0.2 文档校正**：此前文档称「缺少被动 msg_id 时适配器静默丢弃」，这在**服务端**成立，但**客户端适配器实际并不校验时效**，而是依赖进程级永久缓存。这是理解「为什么 WebUI 测试随时能发、每天自动发送却要群活跃」的核心。

读 `qqofficial_platform_adapter.py` 源码确认的行为：

- **永久缓存、无 TTL**：`_session_last_message_id` / `_session_scene` 是适配器实例上的字典，从进程启动到退出一直存在，**没有任何按时间过期的清理**。
- **msg_id 自我延续**：适配器在 `_send_by_session_common` 每次成功发出消息后（包括本插件自己发的通知），会把**那条已发消息的 id 写回** `_session_last_message_id[session]`。于是只要该群历史上有过任何一次收发，缓存里的 `msg_id` 永远非空。
- **`_allow_group_proactive_send` 默认 `True`**：群在 `_session_scene=="group"`（群历史上收过消息即被缓存）时，适配器可**不带 msg_id** 直接走群主动推送。

**对本插件各发送路径的影响**：

| 路径 | 是否离窗口也能发 | 根因 |
|------|------------------|------|
| WebUI「测试发送」/ 手动 `/下线通知 生成 [openid]` | 通常能（群历史活跃过即可） | 适配器借缓存 msg_id 被动回复，或借 `scene=="group"` 主动推送，均不要求当下有入站消息 |
| 每天自动发送（每日流程） | 插件刻意**不**离窗口发 | 仅 `_maybe_fire_windowed` 在窗口内命中入站群消息时调用 `_fire_plan`，且 `_precheck` 默认 `allow_proactive=False` 会拦截无 msg_id 的主动推送；这是**插件设计选择**，非适配器能力限制 |
| `platform_ids` 配错（caps.found=False） | 可能「假成功」 | 插件 `_precheck` 整体跳过（`inspect_qq_official_session` 返回 `applicable=False`），判定权交给适配器，适配器靠缓存照样发出；但若缓存的 msg_id 过于陈旧被服务端拒收，`context.send_message` 可能不返回 `False` → 插件误判成功 |

**结论**：

- 「5 分钟被动窗口」是 **QQ 官方服务端**规则；客户端适配器不校验，所以离窗口发送在适配器层面是可行的，可靠性取决于走「主动推送（无 msg_id，受配额限制）」还是「陈旧缓存 msg_id 被动回复（可能被服务端拒收）」。
- **群 openid 在每日流程里仍然必需**：`_fire_plan` 从 `config.target_groups` 取目标，为空直接不发送，没有默认群。两条路径都需要一个具体群 ID 才能发，区别只在「目标来源」（配置 vs 请求体）与「发送能力是否依赖实时消息」（都不依赖）。
- 若希望每日流程也能离窗口保证送达，应在关窗兜底时以 `allow_proactive=True` 调用 `_fire_plan`（走主动推送而非依赖陈旧 msg_id）；当前版本未启用该兜底。

### 平台实例名（`platform_ids`）

`platform_ids` 是一个**字符串**，填一个 **WebUI「平台适配器」里给适配器起的实例名称**（例如 `松板砂糖（测试用）`），通知只发到这一个平台实例。**不是** `qq_official` 这类类型名。填错会导致 `context.send_message` 返回 `False`——旧版本会把这种情况记成「发送成功」，v1.7.0 起会明确报错。

留空时，插件自动使用**当前唯一一个已启用**的平台实例，并在日志中提示实际生效的名称；多个平台同时启用且留空时不会自动选择，必须显式配置。

### 怎么拿到 openid

让机器人在目标群 / 私聊里收一条消息（@ 它或直接发消息），AstrBot 日志中该会话的 `session_id` 就是 openid。

### 配置体检工具

不启动 AstrBot 也能检查配置是否正确：

```bash
cd data/plugins/astrbot_plugin_offline_notify
python tests/diagnose_live_config.py
```

它会读取真实的 `cmd_config.json` 与插件配置，输出平台解析结果、目标群 / 告警目标的标识校验、被动窗口状态，并在存在阻塞性问题时以退出码 `1` 结束。

### QQ 官方下的告警通道建议

群聊告警在深夜大概率发不出去（群里没人说话 → 无被动 `msg_id`）。**把 `alert_qq` 配成管理员的 `user_openid`**，C2C 私聊主动推送不受 msg_id 限制，是官方协议下最可靠的告警通道。

## 长通知发送策略（合并单条）

> **v2.0.0 起仅支持 QQ 官方平台**，长通知默认**合并为单条**发送，不再逐段拆分。QQ 官方群消息会占用被动回复次数或主动推送配额，逐段发送会成倍消耗配额并易触发频控，因此合并后仅用换行保留分句节奏。

#### 合并策略

- **合并规则**：LLM 长通知先按句切分（`。！？ ! ? ； ; \n`），再合并为单条（段间以换行分隔），一次性 `context.send_message` 投递；
- **单条直通**：内容较短（无句末标点切分点）时直接单条发送；
- **模板回复**：走模板回退的消息始终单条纯文本发送，不做切分/合并处理；
- **多群并行**：`send_to_groups` 对每个目标群独立发送，互不影响。

#### 内容规范化（与 splitter 协同的兼容层）

若您**同时**启用了 `astrbot_plugin_splitter`，本插件在生成 / 渲染通知后仍做一层「无信息损失」的规范化，使内容对 splitter 友好（避免被整体保护或切出空段）：

- **句末标点闭合**：确保每句、以及整段通知以句末标点结尾，分段后的最后一段也是完整句子。
- **去除结构性包裹**：自动剥离 Markdown 代码块（`` ``` ``）与思维链标签（`<think>`），保留正文内容。
- **折叠连续标点**：将连续相同的句末标点（如 `。。。`、`！！`）折叠为单个，避免空段或纯标点碎片。
- **折叠空行**：将 2 个以上连续换行合并。
- **正文零丢失**：仅做格式层规整，称呼、时间、祝福语等真实内容不做任何删改。

#### 提示词约束（v1.5.0 起：通用中立默认 + 明置/多方案）

LLM 生成提示词（`DEFAULT_PROMPT`，即 `custom_prompt` 默认值）为**通用、中立的功能引导**，不含任何特定人设 / 语气风格，仅规范基本指令与输出形式；自动与手动通知共用，并支持在配置面板用 `custom_prompt` 覆盖：

- **通用引导**：以「文本生成助手」定位，目标为生成一段简洁的「暂时离开群聊」离场说明，不设定年龄、性格、口吻等人物设定；
- **禁用词**：AI、人工智能、机器人、助手、通知、系统、**下线**、离线、退出登录、挂机；且不写「XX:XX 下线」这种带具体时刻的写法；
- **昼夜情境**：由 `{time_context}` 注入（深夜去睡觉 / 傍晚休息 / 下午有事 / 上午有事），自然说明离开理由，不暴露后台调度语义（不塞 `offline_time` / `countdown_minutes`）；
- **格式合规**：纯文本、无 Markdown / `<think>` 标签 / 前缀解释；长内容由插件按句自动分段发送；
- **自定义（v2.0.0）**：可在配置面板填写 `custom_prompt` 覆盖内置默认（优先级：配置自定义 > 内置默认）。

这样既不暴露 AI 身份、也不写具体下线时刻，输出为 1-2 句离场说明，经本插件按句分段（或 splitter）输出。

#### 验证

内置测试 `tests/test_splitter_compat.py` 覆盖三类验证：

1. **`split_long_message` 自分段单测**：含用户真实反馈案例（约 70 字符通知正确切成 3 段）、语义完整、无空段 / 纯标点碎片、各前段以句末标点闭合、空串与无分隔符边界。
2. **`GroupNotifier.send_to_group` 集成测试**：验证多段内容确实以**多条独立 `send_message` 调用**投递到正确的群组 UMO，且拼接后内容无丢失。
3. **真实 splitter 管线集成测试**：用 splitter 插件源码验证规范化后的内容能被 splitter 正确分段（仅作兼容性保底）。

## 常见问题

### Q: 修改配置后不生效？

A: 修改 `_conf_schema.json` 中的默认值后，需要**重启 AstrBot** 才能生效。如果是在 WebUI 配置界面中修改，保存后也需要重启插件或 AstrBot。

### Q: 通知没有发送？

A: 按以下步骤排查：

1. 检查「目标通知群组」中是否填写了正确的群 openid（32 位十六进制串）
2. 检查对应群组的 `enabled` 开关是否为开启状态
3. 使用 `/下线通知 计划 列表` 确认计划是否存在且已启用
4. 确认当前是否处于该计划的时间窗口内（对比当前时刻与「下线时间 ± 窗口提前/延后」）
5. 在私聊里用 `/下线通知 生成 <群 openid>` 手动发送一条通知验证

### Q: 如何只在工作日发送通知？

A: 在「定时通知计划」中，将工作日计划的 `day_type` 设为 `weekday`，将周末计划的 `enabled` 设为关闭即可。

### Q: 告警通知收不到？

A: 检查「自我监控配置」中的「告警通知群 openid」或「告警通知 openid」是否已填写。注意：私聊告警需要确保机器人能与该用户私聊。

### Q: 支持哪些平台？

A: 自 **v2.0.0** 起仅支持 **QQ 官方机器人**（`qq_official` / `qq_official_webhook`），不再支持 `aiocqhttp`（OneBot/NapCat/go-cqhttp）。

### Q: 为什么通知不按我设的下线时间准点发送？

A: 这是 v2.0.0 的**被动窗口事件驱动**设计：插件不再「到点主动推送」，而是划定 `[下线时刻 − 窗口提前开启, 下线时刻 + 窗口延后关闭]` 的时间窗口，窗口内目标群有人发言（产生新鲜 msg_id）才触发发送。若窗口内始终无人发言，则本次不发送（插件 `_precheck` 默认 `allow_proactive=False`，会拦掉无 msg_id 的主动推送，并无兜底发送）。注意：**「缺少被动 msg_id 适配器静默丢弃」是 QQ 官方服务端规则**；客户端适配器本身在 `scene=="group"` 缓存下可主动推送（详见上文「会话缓存」），故「每天自动发送要群活跃」是插件刻意设计，而非适配器做不到离窗口发送。通知的「实际发送时刻」由窗口内第一条命中消息决定，而非固定的下线时刻。

### Q: 触发时机浮动会导致通知发送太晚吗？

A: 不会。插件刻意把浮动上限限制在 0-5 分钟（配置范围即 0-5），使每日流程始终借窗口内「新鲜」消息的被动窗口发出。「5 分钟有效期」是 **QQ 官方服务端**对被动回复的约束；客户端适配器不校验时效（详见「会话缓存」），但本插件的事件驱动设计让每日发送天然落在该窗口内，不会超出有效期。

### Q: 多个计划窗口重叠时会怎样？

A: 每个计划独立维护自己的窗口与每日去重状态，互不干扰。同一目标群在重叠窗口内发言时，会分别触发各自的计划（各发一条），不会相互吞掉。

### Q: LLM 生成的通知内容不好怎么办？

A: 可以关闭「启用 LLM 生成通知」开关，系统将使用模板引擎发送通知。模板内容可在「消息模板」配置中自定义。

### Q: LLM 生成太慢怎么办？

A: 可以调整 LLM 调用超时时间（默认 15 秒），或切换到更快的 LLM 模型。如果 LLM 超时，系统会自动回退到模板消息，不影响通知送达。

### Q: 触发时机浮动设为 0 时通知内容合理吗？

A: 合理。浮动设为 0 表示检测到目标群发言后立即发送；通知正文始终由 LLM / 模板生成，不会出现「XX 分钟后」这类依赖提前量的字眼。

### Q: 如何查看通知的发送历史？

A: 在 WebUI 插件页的「通知发布记录」表格查看，每条含触发方式、消息来源与发送结果；原始数据持久化在插件数据目录，可直接查看 JSON。

### Q: 如何升级到 v2.0.0？

A: v2.0.0 为**破坏性重构**，不向后兼容旧配置。请手动更新配置：

1. 删除旧的 `global_advance_minutes`、`global_float_range`、`qq_official_config` 配置项；
2. 新增 `window_before_minutes`、`window_after_minutes`、`trigger_float_minutes`（默认 30 / 30 / 5）；
3. 确认 `target_groups` 中的目标群已改为 **openid**（不再是数字群号）；
4. 重启插件，计划会自动从旧配置导入（`schedules.json`）。

### Q: 如何在私聊中手动向指定群发送通知？

A: 使用 `/下线通知 生成 [群 openid]` 命令（例如 `/下线通知 生成 <32 位 openid>`），仅管理员可用。系统与自动调度**共用同一条提示词**（`custom_prompt` / `DEFAULT_PROMPT`）生成通知。LLM 生成失败时自动回退到模板消息。

### Q: 调度器心跳是什么？

A: 调度器内部有一个独立的心跳任务，每 60 秒更新一次心跳时间戳。监控器通过检查心跳年龄来判断调度器的事件循环是否仍在正常运行。如果心跳超时（默认 180 秒），监控器会触发告警通知管理员。

### Q: 长通知会被拆成多条还是合并成一条？

A: 自 **v2.0.0** 起仅支持 QQ 官方平台，长通知默认**合并为单条**发送（换行保留分句节奏），避免逐段发送成倍消耗官方主动消息配额并触发频控。因此群友看到的是一条完整消息而非多条连发，这是预期行为。若一条通知本身没有句末标点切分点（如纯模板短句），也直接作为单条发送。

### Q: 定时计划怎么管理？一定要改 JSON 吗？

A: **不需要改 JSON**（v1.6.0 起）。两种方式任选其一：
1. **QQ 聊天命令**（推荐）：`/下线通知 计划 列表 / 添加 / 删除 / 启用 / 禁用 / 修改`，写操作仅管理员，变更即时热重载；
2. **WebUI 管理面板**：插件页面「定时计划管理」卡片，可视化增删改。

计划数据统一持久化在插件数据目录的 `schedules.json`，不再依赖 JSON 配置。

### Q: 窗口提前/延后与触发浮动在哪里设置？

A: 这三项是**全局统一设置**（v2.0.0 重构）：在配置面板「窗口提前开启」「窗口延后关闭」「触发时机浮动」中填写，所有计划统一生效。计划本身只关心「何时下线」（下线时间 + 日期类型），不再有独立的提前分钟 / 浮动字段。

### Q: 用命令改时间时，冒号格式有讲究吗？

A: 没有讲究，已做容错（v1.6.0 修复）。以下写法都能正确解析为 `22:30`：
- `22:30`（标准）
- `22: 30`（冒号后有空格）
- `22：30`（中文全角冒号）

命令解析时会先统一中文冒号、再去除冒号两侧空格，所以怎么打都不会触发 LLM 误回复。

### v2.0.2（2026-09-15）

**文档校正：QQ 官方适配器的会话缓存与离窗口发送**

- 📝 **纠正「缺少被动 msg_id 适配器静默丢弃」**：读 `qqofficial_platform_adapter.py` 源码确认——客户端适配器**不校验 5 分钟时效**，而是永久缓存 `_session_last_message_id` / `_session_scene`（无 TTL），且每次发送后把已发 id 写回缓存；`_allow_group_proactive_send` 默认 `True`，群在 `scene=="group"` 缓存下可**不带 msg_id** 主动推送。因此「5 分钟被动窗口」是 QQ **服务端**规则，适配器层离窗口发送是可行的。

### v2.0.1（2026-09-10）

**关窗不再降级发送 + 修复静默丢弃被误报成功**

- 🐛 **修复「发不出去却记成成功」**：QQ 官方适配器在缺少被动 `msg_id` 且群主动推送不成立时，会 `skip send_by_session` **直接 return**——既不抛异常也不返回 `False`。`notifier._send_single` 只判 `ret is False`，因此这类情况全被记为「成功发送」，还会 `mark_sent()` 导致当天不再重试，并在发布记录里留下假记录。现在 `_precheck` 复刻适配器判定（`has_msg_id` 或 `scene=="group" and _allow_group_proactive_send`），不具备发送条件一律提前判失败并给出真实原因。
- 🗑️ **移除关窗降级发送**（行为变更）：`_on_window_close` 不再调用 `_fire_plan(allow_proactive=True)`，只做 `window_state.disarm()` 并打 WARN 日志。原因：无被动 `msg_id` 时适配器必然静默丢弃，降级主动推送实际一条都发不出去。窗口内没机会 ⇒ 本次不发送。
- 🔧 **主动推送也要过检查**：`allow_proactive=True` 不再跳过前置检查，改为校验适配器是否真的具备群主动推送条件，避免手动「测试发送」在冷群上报假成功。
- 📝 **文案修正**：WebUI 定时任务徽章与栏目说明、插件描述同步更正——关窗的作用是「清理窗口状态」，不是「兜底发送」。
- ✅ **测试**：`test_qq_official_compat.py` 补全 `_allow_group_proactive_send` 模拟（此前缺失导致测不到放行分支），新增 4 条断言（scene=group 放行 / 冷群拦截 / 拦截原因 / 开关关闭拦截），全量通过。

### v1.7.0（2026-08-08）

**QQ 官方机器人协议（qq_official）原生适配**

- 🆕 **平台能力适配层** `core/platform_compat.py`：运行时识别适配器类型，输出 `PlatformCaps` 能力画像（UMO 形态、分段策略、纯文本策略、段间隔），其余模块只依赖它，实现「一套代码多协议」。
- 🐛 **修复静默失败误报成功**（最严重）：`Context.send_message` 找不到平台实例时**只返回 `False` 不抛异常**，旧代码只捕获异常，因此会打出「成功发送通知到群 XXX」的假日志。现在显式检查返回值，并标记为不可重试（重试也没用），失败原因写入统计。
- 🐛 **修复 `platform_id` 错配**：从 aiocqhttp 切到 QQ 官方后，插件内置默认值 `小砂糖` 与实际实例名不符导致全部通知静默丢失。现在解析失败时自动回退到唯一已启用平台并给出修正建议；`platform_id` 也补进了配置面板。
- 🐛 **修复 openid 被误拒**：手动发送 / WebUI 测试接口原用 `isdigit()` 校验群号，会拒绝合法的 32 位十六进制 `group_openid`。改为按平台形态校验（`validate_target_id`），平台类型未知时放行不误伤第三方适配器。
- 🆕 **被动窗口探测与预警**：QQ 官方群消息需 5 分钟内的被动 `msg_id`，缺失时适配器**静默丢弃**。插件现在发送前主动探测，缺失时提前失败并说明真实原因；同时跟踪各会话最近入站时间，在调度触发前预警窗口是否已关闭。
- ⚡ **分段策略按平台切换**：QQ 官方下长通知**合并为单条**发送（换行保留分句节奏），避免逐段发送成倍消耗官方主动消息配额并触发频控；aiocqhttp 保持逐段发送不变。段间隔 0.8s → 官方 1.5s。
- ⚡ **强制纯文本**：QQ 官方适配器默认按 Markdown（`msg_type=2`）发送，需要事先报备模板。通知内容是纯散文，现强制 `use_markdown(False)`。
- ⚡ **告警通道加固**：告警目标同样做形态校验与真实成败判定；文档明确建议 QQ 官方下把 `alert_qq` 配成管理员 `user_openid`（C2C 主动推送不受 msg_id 限制）。
- 🆕 **配置节** `qq_official_config`：`merge_segments` / `force_plain_text` 开关，可覆盖上述自动策略。
- 🆕 **诊断工具** `tests/diagnose_live_config.py`：不启动 AstrBot 即可体检平台解析、目标标识、被动窗口，发现阻塞问题时退出码为 1。
- 🆕 **状态命令增强**：`/下线通知 状态` 新增发送平台行与 QQ 官方被动窗口诊断块。
- ✅ **测试**：新增 `tests/test_qq_official_compat.py`（8 组 53 项断言，覆盖平台解析/回退、标识校验、静默失败、分段合并、纯文本、告警通道、旧式调用向后兼容），全部通过；既有 `tests/test_splitter_compat.py` 回归全部通过。
